# ADR-0003 — رمز الدخول يُرفق صراحةً فقط

**الحالة:** مقبول · 2026-08-31 · منشور على الإنتاج

## السياق

قبل الفصل لم يكن هناك عميل API موحّد: كل نداء في `web/app.js` كان
`fetch('/api/...')` مباشراً يمرّر `Authorization: Bearer` يدوياً حيث يلزم.

عند توحيد النداءات الستة والعشرين في `web/api.js`، كان المغري أن يرفق العميل
الموحّد الرمز في **كل** نداء — فهو الأبسط والأنظف ظاهرياً.

لكن `POST /api/events` يقرأ الرمز ليقرّر المصير:

```js
const isAdmin = Boolean(req.user && ADMIN_ROLES.includes(req.user.role));
const created = await events.createEvent(payload, { autoApprove: isAdmin, ... });
```

نموذج الموقع العام **لا يرسل رمزاً عمداً**، فتدخل كل مشاركة طابور المراجعة.
لكن رمز الموقع (`negev_token`) قد يحمل دوراً إدارياً إذا سجّل المدير دخوله من
الموقع العام بنفس الهاتف والرمز.

## القرار

`apiFetch` يرفق الرمز **فقط** عند `auth: true`:

```js
function apiFetch(path, options = {}) {
  const { auth = false, tokenKey = 'negev_token', ... } = options;
  if (auth) { /* أرفق الرمز */ }
}
```

و`adminFetch` غلاف يمرّر `auth: true` مع `negev_admin_token`.

نفس القاعدة حرفياً في تطبيق فلاتر: `ApiClient` لا يرفق الرمز إلا عند
`auth: true`.

كل نداء بعد التوحيد يرفق الرمز **تماماً حيث كان يرفقه قبله** — لا زيادة ولا نقصان.

## النتائج

- سلوك المراجعة محفوظ بالضبط: المشاركات العامة تبقى `pending`.
- الثمن: على كل نداء محمي أن يذكر `auth: true` صراحةً — كلفة مقبولة مقابل عدم
  تغيير سلوك أمني بالصدفة.
- **لا تجعل الرفق افتراضياً** في أي عميل جديد. الافتراض الصامت هنا يكسر طابور
  المراجعة دون أن يُظهر أي خطأ.

## البديل المرفوض

**إرفاق الرمز في كل نداء.** أنظف قراءةً، لكنه يغيّر سلوك النشر: مدير يتصفّح
الموقع العام ويرسل مناسبة كان سيراها منشورة فوراً بدل دخولها المراجعة — تغيير
صامت لا يظهر في أي اختبار قائم.
