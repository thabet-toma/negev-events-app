# منصة مناسبات النقب — Negev Events Platform

منصة ويب لأعراس ومناسبات النقب: عرض الأفراح على الخريطة، التفاعلات والتبريكات اللحظية،
دفتر النقوط الخاص لكل مستخدم، ولوحة تحكم للإدارة والمراجعة.

Node.js + Express + MySQL 8 + Socket.IO. الواجهة عربية بالكامل (RTL).

---

## المزايا

| المجال | التفاصيل |
|---|---|
| المناسبات | نشر، بحث، تصفية حسب البلدة والتاريخ، كشف تعارض المواعيد |
| الخريطة | إحداثيات لكل مناسبة + رابط ملاحة Waze مباشر |
| التفاعل اللحظي | تفاعلات وتبريكات تُبثّ عبر Socket.IO لحظياً |
| دفتر النقوط | سجل مالي خاص لكل مستخدم مع تحليلات حسب البلدة |
| الإدارة | مراجعة واعتماد المناسبات، إدارة التعليقات والمستخدمين، بث الإشعارات |

## البنية

المشروع ثلاث وحدات منفصلة: خادم JSON، وواجهة ويب، وتطبيق فلاتر. الخادم عديم
الحالة (JWT، بلا كوكيز) ويخدم العملاء الثلاثة وأي عميل جديد دون تعديل.

```
server/                    الخادم — JSON فقط، لا يخدم أي HTML
  server.js                نقطة التشغيل — انتظار MySQL ← الترحيل ← البذور ← تشغيل الخادم
  src/
    app.js                 تركيب Express والوسائط الأمنية
    config/                إعدادات موحّدة من متغيرات البيئة
    constants.js           بذرة البلدات الأولى، أنواع التفاعلات (البلدات نفسها في جدول `towns`)
    db/
      pool.js              مجمّع اتصالات MySQL (mysql2/promise)
      schema.sql           مخطط قاعدة البيانات
      migrate.js           تطبيق المخطط (آمن للتكرار)
      seed.js              بيانات أولية + حساب المدير (آمن للتكرار)
    middleware/            المصادقة، الأخطاء، رفع الملفات، التحقق من المدخلات
    routes/                مسارات HTTP رفيعة
    services/              منطق العمل والاستعلامات
    realtime/              مركز Socket.IO
    utils/                 السجلات، أخطاء API، مغلّف async، عنونة الوسائط المطلقة
  scripts/                 سكربتات تشغيلية (ترحيل، استيراد munasabatna، توليد أيقونات العلامة)
  test/smoke.test.js       اختبارات شاملة من طرف إلى طرف
web/                       واجهة الويب — تُنشر على استضافة ثابتة مستقلة
  config.js                عنوان الخادم — الملف الوحيد الذي يتغيّر بين البيئات
  api.js                   عميل API موحّد (apiFetch / adminFetch)
  serve.js                 خادم ملفات ثابتة للتطوير المحلي (بلا اعتماديات)
  sw.js                    عامل الخدمة (Web Push واستقبال الإشعارات، وكاش الهيكل للعمل دون اتصال) — يُقدَّم من جذر الموقع
  manifest.json            تعريف التطبيق المثبَّت (PWA) — قابل للتثبيت
  icons/                   أيقونات العلامة، مولَّدة بـ`server/scripts/brand-icons.js`
mobile/                    تطبيق فلاتر — أندرويد و iOS، يستهلك نفس الخادم
  lib/api/                 عميل API وكل نقاط الخادم
  lib/screens/             المناسبات، الخريطة، إضافة، النقوط، الحساب
```

طبقات واضحة: المسار يتحقق من المدخلات، الخدمة تتعامل مع قاعدة البيانات، والوسائط تتولى
الأمن والأخطاء. لا استعلامات SQL داخل المسارات، ولا منطق عمل داخل الخدمات المساعدة.

## التشغيل السريع (Docker — الطريقة الموصى بها للسيرفر)

```bash
cp .env.example .env
```

عبّئ `.env` بالقيم الحقيقية — على الأقل:

```bash
openssl rand -hex 48    # ضع الناتج في JWT_SECRET
```

`JWT_SECRET` و `DB_PASSWORD` و `MYSQL_ROOT_PASSWORD` و `ADMIN_PIN` كلها إلزامية،
وسيرفض `docker compose` الإقلاع بدونها.

```bash
docker compose up -d --build
docker compose logs -f app
```

يقوم `docker compose` بتشغيل ثلاث خدمات: `mysql` (مع فحص صحة)، و `app` الذي لا يبدأ إلا
بعد جاهزية قاعدة البيانات، و `web` الذي يخدم الواجهة عبر nginx. المخطط والبذور تُطبَّق
تلقائياً عند أول إقلاع.

| العنوان | الوصف |
|---|---|
| `http://<server>:8080` | الواجهة الرئيسية |
| `http://<server>:8080/admin.html` | لوحة تحكم الإدارة |
| `http://<server>:3000/api` | الخادم — يستهلكه أي عميل |
| `http://<server>:3000/health` | فحص الصحة (يشمل حالة قاعدة البيانات) |

⚠️ اضبط `PUBLIC_URL` على العنوان العلني للخادم و `CORS_ORIGINS` على أصل الواجهة، وإلا
انكسرت الصور والصوت أو رفض المتصفح النداءات. وفي `web/config.js` اضبط `apiBase`.

منفذ MySQL **غير منشور** خارج شبكة Docker — التطبيق وحده يصل إليه.

## التشغيل محلياً (بدون Docker)

يتطلب Node.js 20+ و MySQL 8 يعمل محلياً.

الخادم:

```bash
cd server
npm install
cp .env.example .env        # واضبط DB_HOST=127.0.0.1 وبيانات الاتصال
npm run db:migrate
npm run db:seed
npm run dev
```

الواجهة، في طرفية أخرى:

```bash
node web/serve.js           # http://localhost:8080
```

الافتراضي في `web/config.js` هو `http://localhost:3000` — يطابق الخادم أعلاه.

## الأمان

- **JWT_SECRET إلزامي في الإنتاج** — الخادم يرفض الإقلاع بدونه.
- رموز PIN مخزّنة بـ bcrypt، ولا تُعاد أبداً في أي استجابة.
- لا توجد أي بيانات دخول ثابتة في الكود؛ حساب المدير يُنشأ من `ADMIN_PHONE` و `ADMIN_PIN`.
- النشر الفوري للمناسبات يتطلب رمز إدارة صالحاً (لا مفاتيح تجاوز).
- `helmet` للترويسات الأمنية، وتحديد معدل الطلبات (أشدّ على مسارات الدخول والتسجيل).
- كل الاستعلامات مُعامَلة (parameterized) — لا دمج نصوص SQL.
- رفع الملفات مقيّد بالنوع والحجم، وأسماء الملفات تُولَّد على الخادم.
- دفتر النقوط مقيّد بمالكه على مستوى الاستعلام نفسه.

### قبل النشر على سيرفر خارجي

1. ولّد `JWT_SECRET` عشوائياً وضعه في `.env`.
2. غيّر `ADMIN_PIN` عن القيمة الافتراضية `9999`، واستخدم رمزاً أطول.
3. اضبط `CORS_ORIGINS` على نطاقك الفعلي بدل `*`.
4. ضع التطبيق خلف Nginx مع شهادة TLS.
5. خذ نسخاً احتياطية دورية لمجلد `uploads` وقاعدة البيانات.
6. لتفعيل إشعارات Web Push (issue #85): ولّد زوج مفاتيح VAPID بـ
   `npx web-push generate-vapid-keys` واحفظه في `VAPID_PUBLIC_KEY` و `VAPID_PRIVATE_KEY` و
   `VAPID_SUBJECT` داخل `.env` — **مرّة واحدة فقط، ولا يُدوَّر الزوج أبداً بعد ذلك**: تدويره
   يُجبر كل مشترك حالي على إعادة الاشتراك من كل أجهزته من جديد. اختياري تماماً — بلا هذا
   الزوج يعمل الخادم بشكل طبيعي، والاشتراك وحده يُرفض برسالة عربية واضحة.
7. لصور Cloudinary (ADR-0008): ضع `CLOUDINARY_CLOUD_NAME` و
   `CLOUDINARY_API_KEY` و `CLOUDINARY_API_SECRET` (من لوحة Cloudinary ← API Keys) في `.env`.
   بها تذهب كل صورة جديدة إلى Cloudinary: الملصق وصورة الفنان وصورة مزوّد الخدمة وشعاره وغلافه
   وصور معرضه (يحوّلها الخادم بعد استلامها)، وصور الألبومات وصور مشاركة الحلقات (رفع مباشر من
   المتصفّح). الصوت
   يبقى على القرص. بلاها، أو إن فشل Cloudinary لحظة الرفع، تُحفظ الصورة على القرص كما كانت ولا
   يفشل النشر، وزرّا الرفع المباشر يردّان برسالة عربية. ولصفحات الحلقات (`/live/e/:id`)
   وصفحات الصور المستقلة (`/p/:id`) وصفحات الألبومات (`/a/:id`) وصفحات الأشخاص
   (`/person/:id`) وصفحات الفيديو (`/v/:id`) يجب أن يوجِّه nginx الإنتاج `/live` و `/live/`
   و`/p` و`/p/` و`/a` و`/a/` و`/person` و`/person/` و`/v` و`/v/` إلى الخادم (السطران في
   ADR-0006، وصفحة الصورة في ADR-0009، وصفحة الألبوم في ADR-0006 «توسيع 2026-10-22»،
   وصفحة الشخص في ADR-0011). **وصفحات الفيديو (`/v/:id`) تحتاج من nginx نفس قسمَي `/p`** —
   `location = /v` و`location ^~ /v/` — وهما مضبوطان على الخادم مع إصدار 2026-10-26.
8. للنشر التلقائي على فيسبوك: `FACEBOOK_PAGE_ID` و `FACEBOOK_PAGE_ACCESS_TOKEN`. ولإضافة صفحة
   ثانية ضع `FACEBOOK_PAGE_ID_2` و `FACEBOOK_PAGE_ACCESS_TOKEN_2` — توكن الصفحة يخصّ صفحة واحدة
   بعينها ولا يصلح لصفحتين.

مثال Nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name events.example.com;

    ssl_certificate     /etc/letsencrypt/live/events.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/events.example.com/privkey.pem;

    client_max_body_size 35m;   # يجب أن يتجاوز UPLOAD_MAX_MB

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;     # ضروري لـ Socket.IO
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

نسخة احتياطية لقاعدة البيانات:

```bash
docker compose exec mysql mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" negev_events > backup.sql
```

## واجهة API

⚠️ **ترويسة `X-App-Version`**: أرسِلها بأي قيمة على كل طلب لـ `GET /api/events` و
`GET /api/map/events` و `GET /api/events/calendar` و `GET /api/events/trending` و `GET /api/events/featured` و `GET /api/events/:id` لرؤية كل أنواع المناسبات. طلب بلا هذه الترويسة
يُعامَل كعميل قديم لا يعرف سوى «عرس» — يُرشَّح إلى هذا النوع وحده، بلا رسالة ولا خطأ (#20 خطوة 4).

### عام

| الطريقة | المسار | الوصف |
|---|---|---|
| `GET` | `/api/events` | المناسبات المعتمدة، مرقّمة (`?town=` `?date=` `?date_from=` `?date_to=` `?search=` `?occasion_type_id=` `?village_id=` `?archive=1` `?upcoming=1` `?page=` `?limit=` `?sort=newest`) — `?town=` و `?occasion_type_id=` و `?village_id=` تقبل كل منها قيمة واحدة أو قائمة مفصولة بفواصل (سقف ٢٠ قيمة لكل معامل، #85 دفعة 5). **ومناسبة `publish_at` مستقبلي غائبة عن كل قائمة عامة حتى موعدها** (تذكرة #167)، وكل صفّ يحمل `is_ended` (شارة «انتهت») و`is_featured` (تذكرة #171: المبرزة النشِطة تتصدّر تغذية محافظتها وحدها)، و`?upcoming=1` يقبل ما انتهى داخل نافذة نوعه `feed_linger_days` — التفصيل أدناه. و`?sort=newest` ترتيب صريح اختياري للرئيسية الجديدة: `created_at DESC, id DESC` — أحدث ما أُضيف أولاً، ولا تتصدّره مناسبة مبرزة — مع بقاء كل المرشّحات والترقيم وقواعد الظهور كما هي؛ وغياب المعامل أو فراغه يبقي الترتيب القائم حرفاً بحرف، وأي قيمة أخرى ← 400 عربية (`قيمة الترتيب غير صالحة`) من قائمة بيضاء في الكود لا من نصّ العميل |
| `GET` | `/api/events/calendar` | تقويم الشهر في الويب والتطبيق (تذكرة #175): `{ days: [{ date, count }] }` — `?month=YYYY-MM` **إلزامي** (صيغة أخرى أو شهر خارج `01`..`12` ← 400 عربية) و`?region_id=` اختياري (بلا تقييد حين يغيب). **الأيام التي فيها مناسبة وحدها** بترتيب تصاعدي، بلا صفوف صفرية. والعدّ على **امتداد المناسبة كاملاً** (`EVENT_SPAN_*`: `event_end_date` و`youth_party_date` وأيام `event_days`) لا على `event_date` وحده — فعمره ثلاثة أيام يُعدّ في الثلاثة — وببوابة الظهور العام وحدها: لا `link_only` ولا غير المعتمدة ولا المجدولة (`publish_at` مستقبلي)، ويتقاطع مع `X-App-Version` كالتغذية والخريطة. اليوم الذي يعدّ فيه ثلاثاً يعيده `GET /api/events?date_from=D&date_to=D` ثلاثاً (الشرط نفسه)، فيتفق التقويم والقائمة |
| `GET` | `/api/events/trending` | «الأكثر تفاعلاً هذا الأسبوع» في الويب والتطبيق (تذكرة #177): `{ events, window_days: 7 }` — **أعلى ستّ** مناسبات بمجموع إشاراتها الأربع **داخل النافذة وحدها**: `reactions.created_at`، و`congratulations.created_at` المعتمدة (`status = 'approved'`)، و`event_reminders.created_at`، و`event_rsvps.updated_at` بجواب `response = 'yes'` (آخر جواب هو لحظة الإشارة). وصفٌّ بلا إشارة واحدة في النافذة **لا يظهر** (`HAVING signal_score > 0`) فالقسم يختفي حين لا نتيجة. وبوابة الظهور العام وحدها (`PUBLIC_EVENT_VISIBLE_SQL_EVENTS`): لا `link_only` ولا غير المعتمدة ولا المجدولة، **والعزاء مستبعد بالعلم `tone` لا بالاسم**؛ ولا شرط «قادم» ولا نافذة بقاء. والترتيب حتمي: المجموع تنازلياً ثم `event_date` ثم `id`. و`?region_id=` صريح اختياري (400 عربية لغير الرقمي)، وغيابه يأخذ محافظة الاكتشاف (`X-Region`/الحساب/الافتراضية) و`?all_regions=1` يوسّع. الصفوف شكل كرت التغذية نفسه حرفياً (`is_ended` `is_featured` `reactions` `congratulations_count` `honorees` `rsvp_going_count` …)، ويتقاطع `X-App-Version` معها كالتغذية |
| `GET` | `/api/events/featured` | «الأعراس المميزة» (المناسبات المبرزة النشِطة): `{ events }` — المناسبات المعتمدة العامة التي بلغ `publish_at` موعدها، ولم تنتهِ بعد (`EVENT_SPAN_END >= CURDATE()`)، وإبرازها نشِط (`featured_until >= CURDATE()`)، مرتّبةً بـ`event_date ASC, id ASC` وبحدٍّ تقني لحجم الردّ (`FEATURED_EVENTS_LIST_LIMIT = 30`). و`?region_id=` صريح اختياري (400 عربية لغير الرقمي)، وغيابه يأخذ محافظة الاكتشاف (`X-Region`/الحساب/الافتراضية) و`?all_regions=1` يوسّع. الصفوف شكل صفوف trending/التغذية نفسه حرفياً (`is_featured: true` على كل صفّ، والوسائط مطلقة)، ويتقاطع `X-App-Version` معها كالتغذية؛ وبلا نتيجة يعود `events: []` |

الوقت ثم `position`** (تذكرة #176 — ولهذا يسمّيها العميلان «برنامج المناسبة» ويجمعان محطّات كل
تاريخ تحت تاريخها). الحقل ظاهر
واختياري في كل الأنواع افتراضياً، و`سهرة الشباب` (`youth_party_date`) باقية حقلاً مستقلاً كما هي.
في `PATCH` تستبدل القائمةُ المرسَلة الأيامَ كلها، و`[]` تمسحها، وغياب المفتاح (كل APK منشور قبلها)
لا يلمسها. `honorees` و`extra_days` تُقبَلان أيضاً نصّ JSON داخل `multipart`.

⚠️ **منتقي خريطة بدل خطوط الطول والعرض المكتوبة يدوياً (#20 خطوة 6):** `latitude`/`longitude`
في `POST /api/events` و `PATCH /api/events/:id` باقيان بنفس الاسم والشكل، لكن `parseCoordinate`
صار يرفض قيمة **مرسَلة وغير صالحة** (خارج المدى أو ليست رقماً) برسالة عربية بدل ابتلاعها
بصمت إلى `null` — الغياب التام للحقل ما زال يُقبل ويُحفَظ `null` (أو مركز البلدة الاحتياطي)
كما كان دائماً. كلا المسارين يحسبان أيضاً **تنبيهاً ليّناً** على الخادم (Haversine، بلا
تبعية خارجية): إن كان أقرب مركز بلدة للإحداثية المُرسَلة غير البلدة التي اختارها المستخدم،
تحمل الاستجابة `location_warning: { nearest_town, message }` — **بلا رفض وبلا تصحيح تلقائي
للبلدة**؛ تطابق ⇒ `location_warning: null`. البلدة `'القرى والتجمعات'` بلا مركز في
جدول `towns` عمداً فلا تُنتج تنبيهاً أبداً بهذا الاتجاه.

⚠️ **تغيّر عقد `GET /api/events` جذرياً (#20 خطوة 4):**

- **حدّ «القادم»** (`?upcoming=1`، وهو خيار «القادمة فقط» في التغذية؛ بلا هذا العلَم تعود
  القائمة كلها بالقادم أولاً ثم المنتهي): آخر أيام المناسبة `>= CURDATE()` — و«أيامها» هي امتداد واحد من أقدم
  إلى أحدث `event_date` و`event_end_date` و`youth_party_date` وكل يوم في `event_days`
  (ثوابت `EVENT_SPAN_*` في `events.service.js`؛ نفس القاعدة للخريطة وإعلانات التعديل وانتهاء
  صفحة المشاركة وأرشيف الأعراس). مناسبة منتهية غائبة، وعزاء بدأ أمس ويمتد اليوم أو عرس مضى
  يومه الرئيسي وحنّته لا تزال قادمة يبقى ظاهراً. للوصول إلى المنتهي: `?archive=1`
  (يقلب الشرط ويرتّب الأحدث انتهاءً أولاً).
- **فلتر التاريخ** (`?date_from=` و/أو `?date_to=` بصيغة `YYYY-MM-DD`): مناسبة يتقاطع امتداد
  أيامها (أعلاه) مع النطاق، لا تاريخ البداية وحده — عزاء متعدّد الأيام، ويوم إضافي، وسهرة الشباب كلها تُدخلها. النطاق **يحلّ
  محلّ** شرط القادم/المنتهي لا يتقاطع معه: يوم مختار في الماضي يعيد مناسباته بلا `?archive=1`،
  و`?archive=1` معه لا يغيّر إلا الترتيب. بداية بعد النهاية 400 برسالة عربية. `?date=` القديم
  (يوم واحد، داخل شرط القادم) باقٍ كما هو.
- **نافذة البقاء في التغذية وحدها** (تذكرة #167): حدّ «القادم» (`?upcoming=1`) صار «نهاية أيام
  المناسبة لم تتجاوز اليوم ناقص `occasion_types.feed_linger_days` أيام». مناسبة «نجاح» منتهية منذ
  ثلاثة أيام تبقى فيه (نافذتها ٧، يزرعها الترحيل)، ومنذ ثمانية لا تظهر، والعرس المنتهي أمس لا يظهر
  (نافذته ٠). **ولا يُعمَّم**: الخريطة (`GET /api/map/events`) و«قائمتي» والتذكيرات و`related`
  و`sitemap` كلها على `span_end >= CURDATE()` كما هي — «انتهت» كلامُ تغذيةٍ لا خريطةٍ. وكل صفّ في
  هذه التغذية يحمل `is_ended` (منطقي، محسوب في القاعدة بامتداد الأيام كاملاً) فتقول الكرتان
  «انتهت» بلا أن يحسب العميل الحدّ بنفسه.
- **النشر المجدول** (تذكرة #167): مناسبة `publish_at` مستقبلي — معتمدة كانت أو في الطابور — غائبة
  عن **كل** قائمة عامة (هذه التغذية، والخريطة، والبحث، و«مناسبات أخرى»، وخريطة الموقع، وعدّادات
  الاكتشاف) حتى يبلغ موعدها، وتُفتح برابطها وبمعرّفها في `GET /api/events/:id` كمناسبة «بالرابط
  فقط». والشرط واحد في `PUBLIC_EVENT_VISIBLE_SQL_*` (`publish_at IS NULL OR publish_at <= ?`،
  والساعة تُمرَّر مُعامَلةً بساعة القدس من `getZonedParts` — لا `NOW()` الذي يقرأ منطقة جلسة
  MySQL) في **قراءات القوائم** وحدها، فلا نسخة ثانية منه في استعلام قائمة. أما بوابات الصفّ
  الواحد للجدولة والإعلان — `publishGateOpen` و`listDueScheduledPublish` و`markAnnounced` في
  `events.service.js` — فتعيد فحص أهلية صفٍّ واحد بنفس الساعة الممرَّرة (`publishNowClock()`) في
  موضعها من `params`، لا بشرط ثانٍ بساعة مخالفة.
- **مرقّمة**: `?page=` (افتراضي 1) و `?limit=` (افتراضي 30، سقف أعلى صلب 100 — طلب أكبر
  يُقصّ لا يُرفض). الاستجابة تحمل `pagination: { page, limit, total, totalPages }` إلى جانب
  `events`.
- **فلتر نوع صريح**: `?occasion_type_id=` يُطبَّق على الخادم لا العميل، حتى لا ينكسر الترقيم.
- **فلترة متعددة القيم** (#85 دفعة 5، القصتان 40 و43): `?town=` و `?occasion_type_id=` و
  `?village_id=` تقبل كل منها قيمة واحدة (سلوكها كما هو تماماً — `IN` بعنصر واحد) أو قائمة
  مفصولة بفواصل تُبنى `IN (?, ?, …)` بعدد عناصرها فعلياً — لا دمج نصوص أبداً. السقف ٢٠ قيمة
  لكل معامل، محسوباً على ما أُرسل فعلياً **قبل** طيّ التكرار (فتكرار نفس القيمة ٢١ مرة يُرفض
  رغم أنه يختزل إلى قيمة واحدة بعد الطيّ) — تجاوزه 400 برسالة عربية، لا قصّاً صامتاً للعشرين
  الأولى. القيم المكرَّرة نفسها تُطوى إلى نسخة واحدة قبل الاستعلام. `?town=` يقبل أيضاً
  `'الكل'` داخل القائمة، وتبقى معناها «بلا فلتر بلدة» كما لو أُرسلت وحدها؛ أي قيمة بلدة أخرى
  **لا تُتحقَّق من جدول البلدات** — على عكس النشر، لأن البلدات منسوخة يدوياً في
  `mobile/lib/config.dart` وقد تنحرف عن نسخة تطبيق منشورة لا يمكن تحديثها فوراً؛ قيمة بلدة
  غير معروفة تطابق لا شيء بصمت (200 وقائمة فارغة)، لا 400 يُسقط التغذية كلها. قيم
  `occasion_type_id` و `village_id` تمرّ عبر نفس `parseId` الموجود، فقيمة غير رقمية أو ≤ 0
  تُرفض بـ400. `?town=` و `?village_id=` معاً **اتحاد لا تقاطع**: `village_id` غير NULL فقط
  تحت بلدة `'القرى والتجمعات'`، فلو كان الشرطان AND لكانت أي بلدة محدَّدة مع قرية معاً تُعيد
  صفراً دائماً — وهو بالضبط اختيار «رهط + قرية واحدة» من منتقي مكان واحد (القصتان 40/41).
  `?occasion_type_id=` كقائمة يتقاطع مع ترشيح `X-App-Version` أدناه لا يتجاوزه — عميل قديم
  يطلب نوعاً غير مدعوم ضمن القائمة يحصل على نتيجة فارغة، لا موسَّعة. نفس القواعد على
  `GET /api/map/events` حرفياً.
- **حقلان جديدان على كل صف**: `congratulations_count` (عدد صحيح، صفر لا غياب) و
  `latest_congratulation` (`{sender_name, message, created_at}` أو `null`، الأحدث فقط) —
  محسوبان باستعلام نافذة واحد (`ROW_NUMBER` + `COUNT` عبر `PARTITION BY event_id`)، لا
  `JOIN`. يختفي الحقلان معاً من الصف حين يكون `show_congratulations_count` مطفأً على نوع
  المناسبة — لا حسب اسم النوع.
- **ترشيح حسب نسخة العميل** (#11): طلب بلا ترويسة `X-App-Version` (كل تطبيق منشور اليوم)
  يستلم من `GET /api/events` و `GET /api/map/events` **مناسبات النوع الأول بالترتيب
  (`position`) فقط** — وهو «عرس» حالياً، لكن الاشتقاق بالبيانات لا بالاسم. طلب تفاصيل مناسبة
  من نوع آخر (`GET /api/events/:id`) بلا الترويسة نفسها يُرفض بـ404 ورسالة «هذه المناسبة
  تحتاج نسخة أحدث من التطبيق». طلب يحمل الترويسة (أي قيمة) يرى كل الأنواع بلا تغيير — قيمتها
  الفعلية غير مقروءة، وجودها فقط هو ما يُعلن عميلاً حديثاً.
- **أعمدة صريحة**: `secondary_location_name` و `created_by` و `updated_at` و `status` لم
  تعد في صفوف هذه القائمة (لا يعرضها أي عميل) — كل حقل تقرؤه الواجهات الحالية
  (`groom_name`, `title`, `family_clan`, `dinner_time`, `poster_url`, `audio_url`, …) ما زال
  موجوداً. `GET /api/events/:id` غير متأثر ويعيد كل الأعمدة كما كان.
- **«جاي / مش جاي» على الصفّ** (تذكرة #168، ADR-0015): `rsvp_going_count` (عدد صحيح) = **مجموع `party_size`** في أجوبة «جاي» على المناسبة، لا عدد الأجوبة — و`party_size` نفسه **إجمالي الحاضرين بمن فيهم صاحب الجواب** — في القائمة والتفصيل معاً. **يغيب المفتاح كلياً** حين يكون `show_rsvp_count` مطفأً على نوع المناسبة، **أو `rsvp_enabled` مطفأً** (الميزة المغلقة تُخفي عدّادها كما تُخفي نموذجها وزرّها، ADR-0015 §3)، ولا يظهر إطلاقاً لنوع `tone = 'solemn'` (عزا) — الغياب لا الصفر، كما يفعل `followers_count` تماماً. و`GET /api/events/:id` يضيف لصاحب الجلسة `my_rsvp` (`{response, party_size, source}` أو `null` = «لم يُجب بعد») حين يكون النوع مفتوحاً؛ والزائر لا يستلم المفتاح أصلاً. المسارات الثلاثة في جدول API أعلاه.
- **الدعوات الشخصية «أهلاً فلان»** (تذكرة #183، والمواصفة #156 مرحلة ٣): صاحب المناسبة يكتب أسماء ضيوفه (اسم في كل سطر) فينشئ الخادم لكل اسمٍ دعوةً برابط `/e/:id/i/<token>` — توكِن ٣٢ حرفاً hex **عشوائياً من `crypto` لا مشتقّاً من الاسم ولا من المعرّف**، فمن لا يملك رابطه لا يفتحه. الصفحة تقول «أهلاً \<الاسم\>» وتضع الاسم مسبقاً في نموذج الحضور نفسه من #169، والجواب يُرسَل إلى `POST /e/:id/rsvp` القائم (لا مسار كتابة ثانٍ) فيكتب `event_rsvps.invite_id` ويعود إلى صفحة الدعوة. أول فتح يكتب `opened_at` **مرة واحدة**، و«مين جاي» تعرض لكل صفٍّ دعوته وحالتها، وقائمة الدعوات تعرض جواب كل دعوة. **حذف الدعوة لا يحذف الجواب** (`ON DELETE SET NULL`). الواجهات: زرّ «الدعوات» في «مناسباتي» في الويب والتطبيق، بنفس شرط «مين جاي».
- **عدّاد «المهتمين» يخرج باسمين متطابقين**: `interested_count` (اسم المواصفة، تذكرة #168) و`followers_count` (الاسم الذي يقرأه كل عميل منشور) — الرقم نفسه، عدد صفوف `event_reminders` أي «ذكّرني»، تحت علَم `show_followers_count`، ويغيب الاثنان معاً حين يُطفأ العلَم. لا عمود موازٍ ولا عدّاد ثانٍ: `interested_count` مرادف يُضاف مع القديم لا بديلاً عنه، فلا ينكسر APK قائم.
- **عدّادات صفحة المناسبة العلنية** (تذكرة #170): `GET /api/events/:id` صار يحمل `congratulations_count` أيضاً — عدد التبريكات **`approved`** وحدها (لا تبريكة المُرسِل قيد المراجعة، فالفهرس واحد لكل الناس). ويغيب المفتاح كلياً حين يطفئه `show_congratulations_count` على النوع **أو تكون نغمته `solemn`** — الغياب لا الصفر، كأخويه. والواجهات ترسم من الحقول الثلاثة: «جايين» من `rsvp_going_count`، و«مهتمين» من `interested_count`، و«تبريكات/تعازي» من `congratulations_count`؛ ولا عدّاد على العزاء أصلاً.
- **«ذكّرني» على كل صف** (#20 خطوة 7 — متابعة، لا تعهّد حضور، ولا زر «لن أحضر» في هذا
  الدومين): `is_reminded` (منطقي) يظهر دائماً — `true`/`false` للمستخدم المسجَّل عبر
  `Authorization`، و`false` للزائر. `followers_count` (عدد صحيح) — ومعه `interested_count`
  بالرقم نفسه — يظهر **فقط** حين يكون علَم
  `show_followers_count` مرفوعاً على نوع المناسبة — يغيب الحقلان كلياً حين يكون مطفأً (لا صفر)،
  كما يفعل `congratulations_count` تماماً. عزاء اليوم يُطفئه، عرس اليوم يرفعه.
  **صار اسمه في الواجهات «قائمتي»** (زرّ واحد «أضف لقائمتي»/«في قائمتي» وتبويب ثانٍ في
  الشريط السفلي للويب والموبايل) والحقل والمسارات لم تتغيّر. **وفي «قائمتي» قسم «مزوّدون
  محفوظون»** (تذكرة #185) يقرأ `GET /api/services/favorites` ويعرض بطاقات المزوّدين الذين
  حفظهم صاحب الحساب وحده — ويختفي القسم كاملاً حين لا محفوظات، فلا عنوان لقسم فارغ ولا وجهة
  جديدة في الشريط. الصفّ المكتوم (`event_reminders.notify = 0`)
  يبقى متابِعاً — `is_reminded` صحيح ويُحتسب في `followers_count` — لكنه لا يدخل
  `/api/reminders/schedule` ولا العدّاد التنازلي ولا «تحديث على…» ولا إشعار تغيّر التاريخ/المكان — يبقى له في القائمة نفسها
  شارة «تغيّر الموعد» (`date_change`).
- **`announcements`** إلى جانب `events`: إعلانات تعديل التاريخ **الحيّة فقط** لكل مناسبة
  (`is_current = 1` ولم ينتهِ تاريخها الجديد بعد) — راجع قسم «إعلانات تعديل التاريخ» أدناه.
  يخضع لنفس ترشيح `X-App-Version`.

⚠️ **تغيّر سلوك `POST /api/events/:id/congratulate` (#20 خطوة 5):** صار يتطلب رمز دخول
صالح 🔒 — طلب بلا رمز يُرفض بـ401 (كان عاماً). `sender_name` صار يُشتقّ من الحساب دائماً،
لا من جسم الطلب (إدارة فقط تقدر على تجاوزه عبر `sender_name` في الجسم). الحالة الابتدائية
(`pending` أو `approved`) تُقرَّر من علَم `premoderate_messages` على نوع المناسبة — عزاء
اليوم، بلا شرط على اسم النوع في الكود. رسالة `pending` **لا تُبثّ لحظياً** ولا يراها إلا
مُرسِلها (والمالك/الإدارة عبر طابور المراجعة)؛ الجمهور والبحث والعدّاد (`congratulations_count`)
لا يحسبون إلا `approved`. الشارة الافتراضية من `default_badge_title` لنوع المناسبة، وليست
نصاً ثابتاً — نوع بلا شارة افتراضية (كالعزاء) يعطي شارة فارغة، لا «مبارك الفرح» ولا «صديق
العريس». حدّ معدّل: **10 تبريكات لكل مستخدم كل 10 دقائق** (`express-rate-limit`، بالمستخدم
لا بعنوان IP).

و`font_key` و`color` (قوائم مغلقة في الكود لا FKs)، `size` (`ENUM('story','portrait','square','a4')`)،
`photo_url` (الصورة المرسومة على البطاقة، و`NULL` = بطاقة نصّية)، `image_url` (الناتج المخزَّن)،

المولَّدة — ونصّ الصفحة نفسه لا يتغيّر (ADR-0006).

### إعلانات تعديل التاريخ (#20 خطوة 7)

«إعلان التعديل» ليس نوع مناسبة ولا مناسبة جديدة — هو خبر عن مناسبة قائمة. يُنشَر **فقط**
حين يعتمد الأدمن تعديلاً حرِجاً يمسّ `event_date` أو `event_end_date` تحديداً (لا بلدة ولا
مكان) عبر `PATCH /api/admin/events/:id/status`، ويحلّ الأحدث محلّ الأقدم في العرض
(`is_current`) بينما تبقى كل الصفوف في الجدول للتدقيق. يظهر داخل استجابة `GET /api/events`
كحقل `announcements` — لا نقطة نهاية منفصلة — ويختفي تلقائياً بعد مرور آخر أيام المناسبة
بعد التعديل (نفس امتداد الأيام في «يعرض القادم فقط» أعلاه).

تُنشَأ الإشعارات تلقائياً — بعضها في نفس معاملة اعتماد التعديل (تغيّر تاريخ أو مكان، اعتماد
أو رفض مناسبة)، وبعضها من مجدوِل يومي داخل عملية الخادم نفسها (issue #85، دفعة 3):
عدّاد تنازلي (`event_soon`، ٨·٦·٤·٢·يوم المناسبة، **لا يُنتَج أبداً** لنوع مناسبة مطفأ
عليه `notify_countdown` كالعزاء، ونصّه لا يذكر تاريخاً) وملخّص مراجعة يومي واحد
(`moderation_digest`) لكل ناشر لديه رسائل بانتظاره — لا إشعار لكل رسالة — و«قوّي مناسبتك»
الثاني (`event_nudge`، انظر أدناه). المجدوِل عديم
الترتيب وآمن التكرار: كل صفّ يكتبه يحمل `dedupe_key` (`server/src/db/schema.sql`)، فتشغيله
مرّتين لنفس اليوم ينتج صفّاً واحداً لا صفّين. **سقف ثلاثة `event_soon` لكل مستخدم يومياً** —
عن مناسبات لا يملكها المستخدم تحديداً؛ عدّاد عن مناسبته هو، وملخّص المراجعة دائماً (فهو أصلاً
عن محتواه هو)، وأي تغيّر تاريخ أو مكان: كل هذه **مُستثناة لا تُحتسَب أصلاً**، لا مجرّد غير
محظورة — استثناء يبتلعه السقف بصمت أسوأ من عدم وجود سقف (issue #85 مراجعة، FIX 2/3). جمهور كل نوع محدّد بدقّة: من ضغط
«ذكّرني» على المناسبة + مالكها لتغيّر التاريخ/المكان — لا أحد غيرهما، ولا صفّ لمن قام
بالتعديل بنفسه — والناشر وحده لاعتماد/رفض مناسبته. ومنذ 1.11 أربعة أنواع أخرى:
**«مناسبة جديدة»** (`event_new`) لكل مستخدم أبقى `notify_new_events` مفعّلاً **من محافظة
المناسبة نفسها أو بلا محافظة** (تذكرة #161: `users.region_id` يقيّد الصفّ والدفع، ومن لم يختر
محافظةً يتلقّى الكل كما كان) عدا الناشر، عند
**أول** اعتماد فقط (`events.first_approved_at` — إعادة الاعتماد بعد رفض لا تُعلنها ثانيةً ولا
تنشرها على فيسبوك ثانيةً)، وأول ثلاث مناسبات **تُعلَن** في اليوم في محافظة المناسبة فرادى ثم ملخّص لكل مستخدم في
كل محافظة (`event_new_digest`، مفتاحه `event_new_digest_<اليوم>_<regionId>` فلا تكتب محافظةٌ فوق أخرى؛
ومن بلا محافظة يتلقّى ملخّصاً مستقلّاً لكل محافظة بعددها) يتحدّث في مكانه ويعود غير مقروء، ويُدفَع للأجهزة أول مرّة فقط لكل محافظة. **ومناسبة
`link_only` لا يصلها إشعار «مناسبة جديدة»** (تذكرة #166): لا صفّ `event_new` ولا ملخّص ولا دفع
ولا إشارة لحظية — إعلانها يُعلِن وجودها لمن لا يراها — ولا تستهلك واحدة من الثلاث الفرادى ولا تدخل
في عدّ `extra`، لأن العدّاد يعدّ المنشور العلني وحده في المحافظة. ولا يمتدّ ذلك إلى Facebook: عند تفعيل النشر
التلقائي لا يمنعه `visibility` حالياً، وقرار شمل `link_only` به معلّق؛
**ومناسبة `publish_at` مستقبلي لا تُعلَن عند الاعتماد** (تذكرة #167): يُكتب `events.announced_at`
مع صفوف إعلانها في معاملة واحدة، ومجدول النشر (`jobs/scheduler.js`) — إيقاعه المستقلّ كل دقيقة،
لا الجولة اليومية عند 09:00 وحدها — يُعلنها **حين يبلغ موعدها** صفوفاً وإشارة لحظية ودفعاً،
مرّة واحدة؛ وتشغيل الجولة مرّتين لا يضيف صفاً ولا يبثّ ولا يدفع ثانياً (الحجز ذرّي:
`announced_at IS NULL`)، وفشلُ الإعلان يتراجع بالحجز فيُعاد في الدورة التالية بدل أن يُفقد،
وإعادة الاعتماد أو تغيير الموعد لاحقاً لا تُعلن مناسبةً أُعلنت؛
**«تحديث على…»** (`event_updated`) لمتابعي «ذكّرني» عند تعديل تبقى معه المناسبة منشورة، عدا
من عدّل، صفّ واحد لكل متابع في اليوم يتحدّث بآخر تعديل ويعود غير مقروء (تعديل التاريخ/المكان يصل عند اعتماده كما سبق)؛
و**«قوّي مناسبتك»** (`event_nudge`) لناشر مناسبة معتمدة ينقصها ما يعرضه نوعها (سهرة الشباب،
الصورة، الشيلة، الفنان، رقم التواصل، وقت العشاء، اسم المكان — أهمّ اثنين)، عند الاعتماد ثم
مرّة أخيرة بعد يومين إن بقي النقص، ولا شيء لنوع حزين ولا قبل الموعد بأقل من يومين.
**جانب الخادم من التسليم عبر Web Push
(`server/src/services/push.service.js` + `server/src/realtime/announce.js`، issue #85 دفعة 4)
جاهز الآن** — كل إشعار **أُدرِج فعلاً** (لا صفّاً كبته `dedupe_key`) يُدفَع فوراً لكل اشتراكات
المستخدم المسجَّلة، بمحاولة إعادة واحدة محدودة عند 429. **جانب المتصفح عبر Web Push
(`web/sw.js` في جذر الموقع مع طلب الإذن في `web/app.js` والتحكّم في مركز الإشعارات، issue #85 دفعة 6c)
جاهز الآن** — يستقبل `web/sw.js` دفعة الإشعار بالخلفية وينقل المستخدم إلى المناسبة عند النقر. بلا زوج VAPID مضبوط على
الخادم يبقى كل شيء آخر كما هو تماماً: الصفّ يُكتب دائماً، والاشتراك وحده يُرفض بـ400 عربي ويسلك العميل المسار الهادئ.
**تطبيق الموبايل (APK) لا يصله دفع من الخادم إطلاقاً بهذا المسار ولن يصله مستقبلاً أيضاً** —
القرار المعماري أن المنبّه هناك محلّي بالكامل (`GET /api/reminders/schedule`)، لا عبر FCM.
هذا يترك **حالة واحدة بلا حلّ حتى اليوم**، وهي حالة الخادم الصادقة بها (issue #85's own «الحدّ
الصادق»): تغيّر مصدره الخادم (تأجيل موعد، إلغاء) لمستخدم APK لم يفتح التطبيق منذ التغيير —
سيسمع منبّهه المحلي على الموعد القديم إلى أن يفتح التطبيق فعلياً ويُعاد جدولته. **لا التفافة
هنا تغلق هذه الحالة — [#19](https://github.com/thabet-toma/negev-events-app/issues/19) وحده
يغلقها**، بإضافة FCM كمسار توصيل حقيقي ثانٍ للموبايل. `delivered_at` يبقى `NULL` — هذا العمود
يوثّق تسليم FCM للموبايل تحديداً (#19)، لا نجاح Web Push، ولا يزال خارج نطاق هذه الدفعة.

عنصر التعميم داخل هذه القائمة يحمل شكلاً مختلفاً عمداً عن الإشعار الشخصي — `type: 'broadcast'`
و`broadcast_id` (لا `id` إطلاقاً) و`tone` و`expires_at`، ويبقى فيها بعد انتهاء مدّة شريطه
(issue #85, قصة 30). **قيدان على هذه القائمة وحدها: لا يشمل تعميماً نُشر قبل تاريخ تسجيل
المستخدم، ولا منتهياً منذ أكثر من ٣٠ يوماً — والشريط الحيّ لا يتغيّر.** الفصل بين `id` و`broadcast_id`
مقصود: عدّادا `notifications.id`
و`broadcasts.id` مستقلّان ويتداخلان، فعنصر يحمل `id` وحده كان يجعل عميلاً يخلط بين الجدولين
عند تعليم عنصر كمقروء. **حالة القراءة موحَّدة عبر `is_read` على كلا النوعين** — لعنصر التعميم
هي `broadcast_views.dismissed` نفسها (`PATCH /api/broadcasts/:id/dismiss` أدناه هو فعل
«القراءة» الوحيد الذي يملكه تعميم، فإعادة استخدامه بدل حقل منفصل هو ما يتيح وصول الشارة إلى
صفر حتى لتعميم منتهٍ لم يظهر في أي شريط قط). في الويب والموبايل معاً، النقر على عنصر يعلّمه
مقروءاً ويُبقيه في القائمة باهتاً بلا نقطته الحمراء — لا يحذفه؛ الحذف لـ«مسح الكل» (وزرّ ✕ في
الموبايل) وحدهما.

### شريط الإحصائيات في الرئيسية (تذكرة #172)

| الطريقة | المسار | الوصف |
|---|---|---|
| `GET` | `/api/stats/ticker` | عدد المناسبات **القادمة** الظاهرة للعامة في كل محافظة، والمجموع، ولحظة الحساب: `{ regions: [{ region_id, name, upcoming_count }], total, updated_at }`، ومعها حقلان **إضافيان** لا يُسقطان الشريط عند فشلهما: `prices` (أسعار السوق كما في `GET /api/prices`، أو `null` — تذكرة #189) و`latest_news` (الرئيسية الجديدة): `{ id, title, published_at }` لأحدث خبر من مصدر «آخر خبر» للطلب نفسه — بنفس حلّ محافظة `GET /api/news` (`X-Region`، أو محافظة الحساب لمسجَّل، أو الافتراضية) وبعنصر واحد — أو `null` إن تعطّل المصدر أو خلا من عنصر. لا يتطلب تسجيل دخول |

`PUBLIC_EVENT_VISIBLE_SQL_EVENTS` (معتمدة + عامة + بلغ موعد نشرها) و`EVENT_SPAN_END_SQL_EVENTS`
(آخر أيام المناسبة) `>= CURDATE()` — فلا تُعدّ مناسبة «بالرابط فقط» ولا معلّقة ولا مجدولة ولا
منتهية. وحدّ «قادم» هنا هو الحدّ القائم لا نافذة بقاء التغذية (#167). الكاش في الذاكرة داخل
`stats.service.js` مدّته `STATS_TICKER_CACHE_SECONDS` (٣٠٠ ثانية) ونطاقه العملية لا الطلب:
الطلب التالي خلال المدّة لا يستعلم، و`updated_at` ثابت من لحظة التعبئة. والعقد قابل للتمديد —
وقد أُلحق حقل `prices` بالجسم نفسه (تذكرة #189) بلا تغيير أي حقل قائم. وحين يوجد تعميم حيّ في
`GET /api/broadcasts/live` يعرض الويب والموبايل التعميم مكان الشريط.

### أسعار الذهب والعملات (تذكرة #189)

| الطريقة | المسار | الوصف |
|---|---|---|
| `GET` | `/api/prices` | أسعار السوق لحاسبتَي «خدماتنا»: `{ gold: { k24, k21, k18, currency, source_time }, currencies: [{ code, name_ar, ils_per_unit }], fx_date, stale }` — العملات الست (USD, EUR, GBP, JOD, EGP, TRY) سعرُ الوحدة منها بالشيكل، والعيارات الثلاثة سعر غرامها بالشيكل. لا يتطلب تسجيل دخول ولا محافظة، ولا يمسّ أي جدول: مصدران خارجيان وكاش ذاكرة ساعة واحدة. الطلب الثاني خلال الساعة لا ينادي المصدر، وفشله بعد نجاح يعيد آخر نسخة بـ`stale: true` (ومعها تاريخ المصدر نفسه)، وفشله بلا نسخة محفوظة يردّ **503** برسالة عربية. `GET /api/stats/ticker` يحمل الحقل `prices` نفسه، ويعود `null` وحده عند تعذّر الأسعار بلا نسخة — الشريط لا يسقط |

**المصدران** في متغيّري بيئة (`PRICES_FX_URL` افتراضه `https://api.frankfurter.dev/v2/rates`،
و`PRICES_GOLD_URL` افتراضه `https://api.gold-api.com/price/XAU`): الاتجاه من Frankfurter
`base=ILS` أي عدد وحدات العملة لكل شيكل، فالشيكل لكل وحدة = `1 / rate`؛ وgold-api يعطي دولار
الأونصة، فغرام ٢٤ = `XAU × (1 / rates.USD) ÷ 31.1034768`، و٢١ = ‎×0.875‎، و١٨ = ‎×0.75‎.
**والحساب كله في `server/src/services/prices.service.js`** على نمط «آخر خبر» (بلا SQL)،
والمسار العام في `news.routes.js` لأنه الوجه الثاني لطرف خارجي يُطبَّع ويُكاش لا حساب قاعدة.

**وفي العميلين** أداتان تحت «خدماتنا» (الويب والموبايل): **حاسبة الذهب** (الوزن بالغرام × سعر
العيار، ويُعرض «قيمة المعدن بلا مصنعية» وتاريخ gold-api)، و**محوّل العملات** (شيكل ⇄ العملات الست
بسعر `ils_per_unit`، ويُعرض تاريخ فرانكفورت ومصدره). الأسعار تُجلب عند أول فتح للأداة عبر
`apiFetch`/`NegevApi` وحدهما، و**حين لا تصل تُخفى الأداة وتاريخها وتظهر رسالة عربية واضحة**
بدل حاسبة بسعر مخترع.

مدة الشريحة (**٥ ثوانٍ**) تخرج من الخادم (`slide_duration_seconds` على كل ستوري، افتراضه 5)
حتى لا تُنسَخ كرقم ثابت في كل عميل.

**وموضع الظهور (تذكرة #173):** `stories.placement` (`bar`/`carousel`/`feed`، افتراضه `bar`)
يقرّر أين يظهر الستوري نفسه في العميلين — الشريط كما اليوم، كاروسيل بانرات أعلى التغذية، أو
إعلاناً بين الكروت بعد كل `FEED_AD_INTERVAL` (٨) كرتاً بالتناوب. والمشاهدة والنقر يُسجَّلان
من المواضع الثلاثة كما يُسجَّلان من الشريط. **والعميل الذي لا يرسل `X-App-Version` لا
يتلقّى إلا `bar`** — في `GET /api/stories` وبطاقة الدخول معاً، ترشيحاً في الاستعلام نفسه لا
في العميل.

### قيد المشاهدة الصادقة

الجدول `story_views` يحمل عموداً محسوباً (`viewer_key`, `STORED GENERATED`) يساوي
`COALESCE('u:'+user_id, 'd:'+device_id)`، والقيد الفريد على `(story_id, viewer_key, viewed_on)`.
هذا ليس تفصيلاً: `UNIQUE(story_id, user_id, device_id, viewed_on)` مباشرة لا يعمل، لأن MySQL
يعامل كل `NULL` في فهرس فريد كقيمة مختلفة عن أي `NULL` آخر — فمستخدم مسجَّل (`device_id`
دائماً `NULL`) يمكنه تسجيل عشرات المشاهدات في يوم واحد دون أن يصطدم القيد بنفسه أبداً.
البادئتان `u:`/`d:` تمنعان أيضاً تصادم معرّف مستخدم رقمي مع نص `device_id` يحمل القيمة نفسها
بالصدفة. لهذا السبب بالذات لا يحمل `user_id` مفتاحاً خارجياً على `users` — InnoDB يرفض
`ON DELETE SET NULL`/`CASCADE` على عمود تعتمد عليه خانة محسوبة، و`CASCADE` كان سيُنقص عدّاً
تاريخياً صادقاً بمجرّد حذف حساب مشاهد.

### RTL في عارض الستوري — ما ينعكس وما لا ينعكس

لا سناب ولا ميتا توثّقان سلوك عارضهما بالعربية إطلاقاً؛ المرجع الحاسم إرشادات آبل. **العارض
نفسه خارج نطاق الخادم** (`web/` و `mobile/`) لكن التوثيق التالي يُلزِم كل عارض يُبنى مستقبلاً:

| ينعكس ✅ | لا ينعكس ❌ |
|---|---|
| أشرطة التقدّم — تمتلئ **من اليمين**، وأولها أقصى اليمين | السحب للأسفل للخروج |
| مناطق النقر — **«التالي» يصير يسار الشاشة** | الضغط المطوّل للإيقاف |
| ترتيب الحلقات في الشريط | الصورة نفسها · شعار المعلن · أرقام الهاتف |

⚠️ **فخّان معروفان لأي عارض يُبنى لاحقاً:**

- **فلاتر:** `Directionality` يعكس كائنات الرسم تلقائياً، **ولا يعكس مناطق نقر محسوبة يدوياً**
  (`dx < width / 2`) — هذه تُعكس صراحةً في الكود، وإلا صار «التالي» يمين الشاشة رغم RTL.
- **الويب:** خصائص CSS المنطقية (`inset-inline-start` لا `left`، `margin-inline` لا
  `margin-left`) تعطي الانعكاس مجاناً تحت `dir="rtl"`؛ **`left` و `transform: translateX()`
  المباشرة لا تنعكسان** ويحتاجان قيمة يدوية معكوسة. المقترَح للويب: أسهم وزرّ إغلاق صريحة بدل
  مناطق نقر ضمنية — أوضح بالفأرة من محاكاة لمسة.
- الضغط المطوّل يوقف الشريحة (سلوك إنستغرام)، والمشاركة من زرّ صريح — لا من سحب أو نقر مطوَّل.

**`hours`** — الشكل الوحيد المخزَّن، شكلاً واحداً للأدمن وللعميل: مصفوفة **0..6** فيها عنصر لكل يوم عمل بـ`day` (0 = الأحد … 6 = السبت)، و`closed: true` لليوم المغلق، أو `from`/`to` نصّاً `HH:MM` لليوم المفتوح. التحقّق الصارم في طبقة المسار وحدها (400 عربية)، والخدمة تقرأ كما خُزِّن بلا تخمين. والواجهات تعرضه جدولاً أسبوعياً وتُخفي القسم إن لم يسجّل المزوّد ساعات.

**الرقم وواتساب** — الرقم **لا يخرج في القائمة** (`has_phone` وحده) ويظهر في صفحة المزوّد المفردة وحدها (ADR-0016). وأي رابط واتساب لمزوّد يبنيه الخادم في `GET /api/services/providers/:id/whatsapp` برسالته العربية — ولا يبنيه عميل، ولا يعيد الخادم الرقم منفصلاً معه.

**المشاهدة والمفضّلة** (تذكرة #185) — عدّادا 👁/♥ في بطاقة المزوّد ونافذته من الخادم وحده: `views_count` عمود على `service_providers` يزيد فقط حين يُدرَج صفّ مشاهدة جديد، و`favorites_count` يُحسب من `provider_favorites` لا من عمود مرآة. **المفتاح بلا IP**: معرّف الحساب للمسجَّل، أو `X-Visitor-Id` يحمل معرّفاً عشوائياً يولّده العميل ويخزّنه (الويب: `localStorage` بمفتاح `negev_visitor_id` عبر `crypto.randomUUID()`؛ الموبايل: `shared_preferences` بالمفتاح نفسه)، ولا يُشتقّ المفتاح من `req.ip` ولا يُخزَّن عنوان شبكة في أي عمود. الواجهات تسجّل المشاهدة مرة عند فتح صفحة المزوّد (لا في كل رسم)، وزرّ «احفظ المزوّد»/«محفوظ» يبدّل `PUT`/`DELETE` ويأخذ العدّاد ونصّه من ردّ الخادم. وقسم «مزوّدون محفوظون» في «قائمتي» يقرأ `GET /api/services/favorites` ويختفي كاملاً حين لا محفوظات — لا وجهة جديدة في الشريط.

**التقييمات** (تذكرة #186) — صفّ واحد لكل (مزوّد، مستخدم) في `provider_reviews`، فالتقييم الثاني يعدّل الأول. `phone_confirmed_at` يكتبه الخادم لحظة النشر لأن `confirm_phone` إقرارٌ لا حقل بيانات (ADR-0014)، والنشر فوري `visible`؛ والبلاغات (`provider_review_reports`، صفّ لكل مبلِّغ) تُخفي التقييم عند `PROVIDER_REVIEW_REPORT_THRESHOLD` (3، في `constants.js` على نمط عتبتي التبريكات والصور) — **والمخفي يخرج من القائمة ومن `rating_avg` و`rating_count` معاً**. الويب يعرض «★ المتوسط (العدد)» في بطاقة القائمة، والتوزيع خمسة أعمدة والتعليقات المرقّمة في نافذة المزوّد، وورقة كتابة بنجوم 1..5 وإقرار الرقم وحذف صاحبه؛ والموبايل يعرض الأمر نفسه في صفحة المزوّد وبطاقة القائمة. `similar` صار «مميّز» ثم `rating_avg`. **ورقة الكتابة في الويب `#providerReviewModal`، وفي الموبايل `_ReviewSheet` داخل `service_provider_details_screen.dart`**.

**المزوّد المربوط وردّه على التقييمات** (تذكرة #187، ADR-0016) — **الربط عمودٌ على المزوّد لا دورٌ رابع**: `service_providers.linked_user_id` (FK `users` بـ`ON DELETE SET NULL` مع فهرس)، يضعه السوبر أدمن وحده من اللوحة (حقل «الحساب المربوط» في نموذج المزوّد + «بلا حساب»، ونداؤه `PATCH …/link` وحده — لا يُرسل مع حفظ المزوّد). الحساب المربوط **حساب مستخدم عاديّ** يبقى ينشر ويبارك ويحفظ كما كان، **ولا يحرّر اسم المزوّد ولا صوره ولا سعره ولا فئته ولا بلداته**. و**حذف الحساب يفكّ الربط ولا يحذف المزوّد** (يفعلها القيد الأجنبي، لا كود خاص). `users.role` بلا قيمة `'provider'` أصلاً، و`role` المربوط `user` قبل الربط وبعده. و`reply_body`/`reply_at` في `provider_reviews`: ردّ واحد لكل تقييم يستبدل بالتعديل، يكتبه الحساب المربوط بمزوّد التقييم وحده، والشرط داخل استعلام الخدمة نفسه و**404 لا 403** لغيره. في الويب يظهر الردّ اقتباساً تحت التقييم بزرّ «ردّ على التقييم»/«عدّل الردّ» للحساب المربوط وحده (`can_reply`)، وفي «حسابي» قسم «مزوّدي» من `GET /api/services/my-providers` يفتح نافذة المزوّد نفسها ويختفي كاملاً بلا ربط؛ وفي الموبايل ورقة `_ReplySheet` أسفل التعليق وقسم «مزوّدي» في شاشة الحساب. وصفحة المزوّد المفردة تحمل `is_linked_provider` للمسجَّل كي تعرف الواجهة أتعرض زرّ الردّ.

**«اطلب عرض سعر»** (تذكرة #188، ADR-0016 §3) — جدول `quote_requests` بخمس حالات: `awaiting_offer` ← `offered` (عرض المزوّد: **سعر نصّاً كما يكتبه** + ملاحظة) ← `accepted` | `declined` (قرار الزبون)، و`cancelled` بالإلغاء من `awaiting_offer` أو `offered`. **الحالة تحدّدها قراءة الصفّ بقفل داخل معاملة** (`SELECT … FOR UPDATE`) ثم التحديث، فالعرضان المتيامنان لا يمرّان معاً؛ وأي انتقال غير المسموح **409** بجملة عربية. و**الصلاحية شرطٌ داخل الاستعلام**: `sp.linked_user_id = ?` لطلبات المزوّد، و`q.user_id = ?` لطلبات الزبون — والرفض **404 لا 403**. و`quote_requests` **لا يحمل صفّاً لمزوّد غير مربوط** (ADR-0016، البديل المرفوض 5): طلبه يعود رابط واتساب برسالة بناها الخادم. والإشعارات الثلاثة على خدمة الإشعارات القائمة بأنواع جديدة: `quote_request` (للحساب المربوط عند الطلب)، و`quote_offer` (للطالب عند العرض)، و`quote_accepted` (للحساب المربوط عند القبول). الويب: زرّ «اطلب عرض سعر» في `#providerModal` يفتح `#providerQuoteModal` (تاريخ ومعازيم وملاحظة ومناسبة من `GET /api/my-events`)، وفي «حسابي» قسمان `#accountIncomingQuotesSection` و`#accountMyQuotesSection` بثلاثة تبويبات؛ فتح الرابط في نافذة جديدة (`window.open`) لا في تنقّل داخلي. والموبايل: `_QuoteSheet` في صفحة المزوّد، و`_IncomingQuotesSection` و`_MyQuotesSection` في شاشة الحساب، وكل نداء عبر `negev_api.dart`.

### أحداث Socket.IO

`new_event_created` · `admin_new_pending_event` · `event_reaction_<id>` ·
`new_congratulation_<id>` · `system_broadcast` · `new_notification_<userId>` · `town_broadcast` ·
`system_notification` · `live_status` · `live_poll_<episodeId>`

⚠️ `live_status` و`live_poll_<episodeId>` (البث المباشر): الأولى حمولتها فارغة `{}` بعد أي حفظ يلمس
إعدادات البث — العميل يعيد جلب `GET /api/live` بنفسه. الثانية `{ results, total_votes }` بعد كل صوت
ناجح، **بلا** `my_vote` لأنها تصل كل متصل؛ العميل لا يعرضها إلا لمستخدم صوّت هو نفسه. و`system_notification`
يحمل أيضاً `kind: 'live_started'` (مع `event_id: null`) لإعلان بدء البث.

⚠️ `system_notification` (1.11): إشارة **واحدة عامة** بعد أن تُكتب صفوف «مناسبة جديدة» لمستخدمي
محافظة المناسبة (ومن بلا محافظة) دفعة واحدة (تذكرة #161)، بدل `new_notification_<userId>` لكل
واحد منهم. الحمولة
`{ title, body, event_id }` عن مناسبة معتمدة منشورة للعموم، فلا تسرّب شيئاً؛ العميل المسجَّل
يعيد جلب `GET /api/notifications` بنفسه.

⚠️ `new_congratulation_<id>` (#20 خطوة 5): يُبثّ فقط حين تصير التبريكة/التعزية `approved` —
عند النشر المباشر (نوع لا يراجع مسبقاً)، أو عند اعتماد المالك/الإدارة لاحقاً. رسالة `pending`
لا تُبثّ لأحد.

⚠️ `new_notification_<userId>` (#20 خطوة 7؛ الحمولة تغيّرت في issue #85 دفعة 3): قناة
**بمعرّف المستخدم المستلِم**، لا معرّف المناسبة — تُبثّ فقط لمن كان متصلاً في تلك اللحظة، لأيّ
نوع إشعار شخصي (تغيّر تاريخ/مكان، اعتماد/رفض، عدّاد تنازلي، ملخّص مراجعة). الحمولة **لا تحمل
عنوان الإشعار ولا نصّه إطلاقاً** — `{ id }` فقط — لأن `realtime.emit` بلا غرف ويصل كل عميل
متصل (`realtime/index.js`)، فأيّ نصّ هنا كان يُسرَّب لأيّ عميل يعرف اسم قناة مستخدم آخر. عميل
متصل يعيد جلب `GET /api/notifications` بنفسه ليقرأ العنوان والنصّ الفعليّين — نفس نمط
`town_broadcast` أدناه. من لم يكن متصلاً بالـSocket لكن لديه اشتراك Web Push مسجَّل يصله دفع
فعلي عبر `push.service.js` (issue #85 دفعة 4) بعنوان ونصّ الإشعار نفسيهما؛ من لا اشتراك له
(أو لا زوج VAPID على الخادم أصلاً) لا يصله شيء حتى يفتح التطبيق — الصف نفسه في
`GET /api/notifications` يبقى موجوداً بانتظاره في الحالتين. صفّ ينشئه المجدوِل
(`server/src/jobs/scheduler.js` — خارج `services/` عمداً، لأنه يبثّ بنفسه) يُبَثّ من داخل
ذلك المجدوِل مباشرة، لا من طبقة مسار — هو الطبقة المنسِّقة (orchestrator) الوحيدة له، تماماً
كما تكون طبقة المسار المنسِّقة حين يأتي الإشعار من طلب HTTP؛ لا بثّ من داخل
`notifications.service.js` نفسه في الحالتين.

⚠️ `system_broadcast` مقابل `town_broadcast` (issue #85): `realtime.emit` **بلا غرف — يصل كل
عميل متصل** (`realtime/index.js`)، فنصّ تعميم مخصوص ببلدة لا يجوز أن يمرّ منه أبداً، وإلا وصل
كل مستخدم على المنصّة تعميم بلدة غيره. `system_broadcast` يبقى كما هو تماماً (نفس شكل
الحمولة) وللتعاميم **العامة فقط** — عملاء الويب وAPK المنشورة تستمع له. `town_broadcast`
قناة جديدة **بلا نصّ التعميم إطلاقاً** — تحمل فقط `id` و`scope_town` و`tone` و`expires_at`،
ما يكفي عميلاً ليقرّر إعادة الجلب من `GET /api/broadcasts/live` المرشَّح فعلياً على الخادم.
